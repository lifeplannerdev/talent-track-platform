# Talent Track Platform (powered by F.L.A.G.)

Exam platform for students in Kerala, India (repo and package name still `talenttrackplatform`; the product name in the UI is "Talent Track Platform", never abbreviated; F.L.A.G. is written exactly so, with the final dot, and means Foreign Languages Academy Gurukulam, spelled out once on the landing footer). Spec: `docs/superpowers/specs/2026-11-13-talenttrackplatform-design.md`. Phase 1 plan: `docs/superpowers/plans/2026-11-13-talenttrack-phase1.md`.

## Stack
Next.js 16 (App Router, TypeScript, Tailwind 4), shadcn/ui (Base UI), Supabase (Postgres, Auth, Storage), Vitest, Playwright. Versions are pinned in `package.json`.

## Environments
- Development uses the LOCAL Supabase stack through Docker. No remote Supabase project is created, linked or touched by this repo yet (the existing "lp website" project belongs to another site).
- Production target (later): Supabase in Mumbai (ap-south-1), Vercel region bom1.
- Env vars: copy `.env.example` to `.env.local`. Local API URL is `http://127.0.0.1:54321`; keys come from `npx supabase status`. Only `.env.example` is committed. Mail and invites need `MAIL_TRANSPORT` (`log` or `resend`; default `log` outside production, which sends nothing and logs only the recipient domain), `RESEND_API_KEY` and `MAIL_FROM` (only for `resend`) and `APP_URL` (public base URL for the links in invite emails, no trailing slash; without it no invite link is made and sending reports "failed"). `supabase/config.toml` sets `otp_expiry = 86400` (invite links live 24 h): after changing it restart the local stack (`npm run db:stop && npm run db:start`).

## Data and security conventions
- Every public table has RLS. Anon has no privileges.
- Students never read `questions`, `attempts` or `assignments` directly. They use the views `student_assignments` (their assignments, unmasked since 0020) and `student_attempts` (points, max_points, passed are NULL until status = 'released', which since 0020 is the moment the attempt is scored). The paper itself comes only from server code (`getAttemptForStudent`, German text, no key). `student_questions` was dropped in 0014 (it exposed the English text during an exam); do not add a student view over questions.
- Staff read through RLS scoped by role (see "Roles, trainers and student details"): an admin reads everything, a trainer only their own students' rows. Staff cannot write `attempts`, `attempt_questions`: scoring and attempt creation run in server code with the service role.
- Staff sessions may only INSERT `assignments` with (student_id, curriculum_id, position) and cannot UPDATE or DELETE them (0023): status, extra attempts, repeats, order and removal go through the service-role functions (`record_score`, `give_extra_attempts`, `reorder_curriculums`, `remove_curriculum`). Staff UPDATE on `exam_sets` is column-level without `curriculum_id` (an exam set never moves between curriculums). Since 0025 no session may INSERT or UPDATE `profiles` (the Auth trigger creates them, consent uses the service role), and staff UPDATE on `curriculums` (name, max_attempts) and `questions` (topic, difficulty, stems, options, correct_option_id, points, status) is column-level.
- Profiles are created by the `on_auth_user_created` trigger from `raw_app_meta_data` (role, username, full_name, batch, track, trainer_id), which only the admin API can set. The trigger is a deferred constraint trigger (0003) because the Auth admin API sets app metadata after the insert. Usernames map to internal emails via `usernameToEmail` (`username@students.talenttrack.internal`). Public sign-up is off.
- Questions: German with English translations (`stem_de`, `stem_en`, options `{id, de, en}`).
- Any change to RLS needs a failing test in `supabase/tests/rls.test.sql` first.
- Staff have no DELETE on `profiles`, `curriculums` or `exam_sets` (0012 policies, 0013 privilege, so a staff delete fails with 42501): the foreign keys cascade into attempts without RLS. Removing those rows is a service-role operation.
- Legacy columns: `attempts.granted_by` and `attempts.released_by` are kept for history but unused since 0020 (no grants; record_score releases with no staff id). Do not build on them.
- New functions are not executable by PUBLIC (0013 `alter default privileges revoke execute on functions from public`): every function callers need must `grant execute` explicitly (service_role for the attempt functions).

## Attempts (exam lifecycle, spec change 1)
- Spec: `docs/superpowers/specs/2026-11-18-immediate-marks-attempts-design.md` amends the original spec: no video capture, marks shown at once (no hold, no release step), 2 attempts per curriculum without approval, independent curriculums, a different exam set per attempt.
- `src/lib/attempts.ts` (server only, service role): `startAttempt(studentId, curriculumId)`, `getAttemptForStudent` (resume), `saveAnswer`, `submitAttempt`, `sweepExpired`, `settleAttempts`, `scorePendingAttempt`. Callers authenticate with `requireRole('student')` / `requireStudentWithConsent()` and pass the session user id, never a client id.
- Atomic writes are SQL functions executable only by `service_role` (security invoker, empty `search_path`): `start_attempt(p_student_id, p_exam_set_id, p_draw)` (0020, 0024), `save_answer`, `close_attempt`, `close_expired_attempts`, `record_score` (0020, 0024), `give_extra_attempts` (0021, 0024), `db_now`. Deadlines use database `now()`. `release_attempt` and `grant_attempt` were dropped in 0020.
- Allowance per student and curriculum = `curriculums.max_attempts` (default 2, 1..20) + `assignments.extra_attempts`. Attempts used = the student's attempts with status 'submitted' or 'released' over all exam sets of the curriculum (in progress does not count yet).
- Exam set choice: `startAttempt` settles the curriculum first (lazy expiry, scores any submitted-but-unscored attempt), then picks with `chooseExamSet` (`src/lib/exam-set-choice.ts`) a random exam set the student has not had among those that `canFillPaper`; with `assignments.allow_repeats` and every set used, the least recently used set, and `drawPaper(..., { allowSeen })` takes unseen questions first. `start_attempt` re-checks everything under the assignment lock: `exam_set_not_found`, `not_open` (no assignment), `blocked`, `passed`, `in_progress` (any exam set of the curriculum), `scoring_pending` (a submitted unscored attempt in the curriculum), `no_attempts_left`, `exam_set_used` (unless allow_repeats), `invalid_draw`, `question_already_seen` (only without allow_repeats). TS maps them to `StartError` codes (`calculating` for scoring_pending, `unavailable` when no set can be chosen or the pool is short).
- Submit = close (in_progress -> submitted) then score once with `scoreAttempt`. `record_score(p_attempt_id, p_points, p_max_points, p_passed, p_questions)` stores the scoring snapshot (per attempt question: key, points, topic, awarded points in `attempt_questions.correct_option_id/max_points/topic/awarded_points`; `invalid_snapshot` unless it covers exactly the attempt's questions and adds up), sets status 'released' with `released_at` in the same update, then sets the assignment: pass -> 'passed'; fail and attempts used >= allowance -> 'blocked' (only from 'open'; 'passed' is never downgraded). Returns 'released', or null when the attempt is not submitted-and-unscored (so a double submit or sweep scores once). Readers of per-question or per-topic results use only the snapshot columns, never live `questions` (staff may edit questions after scoring); the columns are staff-only.
- `finalizeAttempt` never scores an attempt without attempt_questions (logs the id; it stays "being calculated").
- Lock order: assignment -> new attempt rows (start_attempt, give_extra_attempts, remove_curriculum, reorder_curriculums lock the assignment FOR UPDATE first; reorder locks the student's rows in id order since 0023); record_score locks the attempt, then the assignment. start_attempt never locks an existing attempt row, so there is no cycle. Keep new functions in this order.
- Students cannot write `answers` directly; saves go through the `saveAnswerAction` server action.
- Expiry is lazy (on every read/save of an attempt and in `settleAttempts`); `/api/cron/sweep` (Bearer `CRON_SECRET`, exempt from the proxy) is a daily backup because Vercel Hobby only allows daily crons. It closes and scores expired attempts and scores any unscored submitted one.

## Percent first and the 90% pass mark (0019)
- Owner rule: results are shown as percentages first; the standard pass mark is 90%. `exam_sets.pass_mark_percent` defaults to 90 (0019) and the New exam set form proposes `DEFAULT_PASS_MARK_PERCENT` (`src/lib/percent.ts`); staff can still set 0 to 100 per exam set. 0019 moved existing exam sets still at 60 (the old form default) to 90 after snapshotting their attempts.
- `attempts.pass_mark_percent` is the pass mark snapshot: `start_attempt` copies it from the exam set at start. Scoring (`finalizeAttempt` -> `scoreAttempt`) and `record_score` use it (falling back to the exam set only for legacy rows with null); `record_score` raises `invalid_outcome` unless `passed = (points * 100 >= pass_mark_percent * max_points)`. Reports read the snapshot: `getStudentResult` (service role after the owner/released re-check, with the topic totals) and `getAttemptReview`. Null only for legacy scored attempts whose outcome disagreed with the exam set at migration time; reports then omit the pass mark. A pass mark changed in the exam set form applies to attempts started afterwards only.
- Helpers (pure, tested in `percent.test.ts`): `meetsPassMark` (exact integer comparison), `formatPercent` ("92%", "66.7%", never rounds up onto a whole number, so 89.95% is "89.9%"), `percentValue` (bar width). Every UI percentage goes through `formatPercent`.
- Privacy: nothing student-facing shows a percentage, points or the pass mark of an attempt before it is scored (in progress or "being calculated"). Students never see the key or per-question results, only totals, percentage and topic totals.

## Results (immediate marks)
- Student: after submit or expiry the student goes straight to `/results/[attemptId]` (`getStudentResult`, `src/lib/results.ts`, `student_attempts` view through the session client; it calls `scorePendingAttempt` first). The per-topic breakdown is read from the scoring snapshot with the service role only after re-checking owner and status; only topic totals are returned. A submitted attempt without a score shows `CalculatingResult` ("Your result is being calculated", test id `result-status`, no numbers). The report is bilingual and has a print stylesheet (`print:` variants plus `@media print` in globals.css).
- `notFound()` inside a Suspense boundary renders the not-found UI with HTTP 200 (streaming); tests check for absence of data, not the status.
- Student start page `/exam/start`: `getExamStartState(studentId)` returns one `CurriculumCard` per assigned curriculum (`{ curriculumId, name, position, kind, attemptsLeft, attemptId? }`, by position; it settles attempts before reading statuses). Kinds, in precedence: `in_progress` (Resume, `resume-exam`), `calculating` (`calculating`), `passed` (latest pass percentage, View result), `blocked` (stored blocked, or open with 0 attempts left; `contact-trainer`), `ready` (`attempts-left` "2 attempts left", Start exam `start-exam`, `startExam(curriculumId)`), `unavailable` (no usable exam set left; `contact-trainer`). Cards are `curriculum-card` with `data-kind`. No forced order and nothing shared between curriculums. "Your results" (`listStudentResults`) groups per curriculum (`results-list`, `results-group`, `result-row`, `result-percent`), percentage first. Empty state `no-exams`.
- Staff Attempts (`/staff/review`, nav "Attempts"): read-only list of every attempt with batch, curriculum and status filters (In progress, Being scored, Passed, Not passed; `ATTEMPT_FILTERS` in `src/lib/attempt-status.ts`), percent first (`listResults` in `src/lib/review.ts`, staff session; test ids `results-table` / `results-empty`). `/staff/results` redirects there (next.config.ts). `/staff/review/[attemptId]` is the bilingual evaluation (`getAttemptReview`; `review-status` Passed / Not passed / Being scored; "Back to attempts"). There is no Release control and no "awaiting review" state anywhere. `/staff/students/[id]` has a Results section (`getStudentDetail().results`, Evaluation links). Shared `ResultScore` / `AttemptStatusBadge` in `src/components/app/result-score.tsx`.

## Blocking and extra attempts
- Blocking is written by `record_score` (above), so a block and the failed result appear in the same transaction. Staff pages also treat an open assignment with every attempt used and nothing in progress or being scored as blocked (`effectiveStatus` in `src/lib/staff-overview-core.ts`, shared by the dashboard, Blocked, Extra attempts and student pages).
- Extra attempts replace grants (the `attempt_grants` table was dropped in 0020; unused grants became +1 `extra_attempts`): `giveExtraAttempts(staffId, studentId, curriculumId, n, allowRepeats)` (`src/lib/extra-attempts.ts`, service role) wraps `give_extra_attempts` (0021): `not_staff`, `invalid_n` (1..10), `not_assigned`, `already_passed`; adds n, `allow_repeats = allow_repeats or p_allow_repeats` (never switched off), blocked -> open only when max_attempts + extra_attempts then exceeds the attempts used (0024); otherwise it stays blocked and `giveExtraAttempts` returns `{ stillBlocked: true }`, which the success message tells staff (give more). Staff can give extra attempts at any time. Repeats are only saved together with at least one extra attempt.
- `giveExtraAttemptsAction({ studentId, curriculumId, n, allowRepeats })` (`src/app/staff/grants/actions.ts`) calls `requireRole('staff')` first. `ExtraAttemptsButton` opens the dialog (count 1..10, "Allow repeating exam sets" switch, on by default when no exam set is left; locked on when already allowed), used on the Extra attempts, Blocked and student pages. Success goes to the page-level live region (`grant-success`), a refusal next to the button (`grant-error`).
- Staff pages (admin and trainer; a trainer sees only their own students' data): `/staff` dashboard (Blocked card, No exam set left, Recent attempts), `/staff/blocked` (attempts used of allowance, exam sets left, last score, "Student page" link), `/staff/grants` "Extra attempts" (`grants-table` blocked students, `short-table` students with attempts left but no usable exam set). Readers in `src/lib/staff-overview.ts` (session client and RLS; pure logic in `src/lib/staff-overview-core.ts`). "Exam sets left" everywhere counts only unused exam sets that `canFillPaper`.

## Roles, trainers and student details (v2 phase 1)
- Spec: `docs/superpowers/specs/2026-11-24-v2-roadmap-and-foundation-design.md`. Roles are `admin`, `trainer`, `student` (`profiles.role`, migration 0026 turned every old `staff` row into `admin`). "Staff" is no longer a stored role: it means admin or trainer. `src/lib/auth/roles.ts` (pure, safe for the proxy and client code) has `Role`, `RoleGroup` (a role or `"staff"`) and `isStaffRole(role)`. `requireRole('staff')` passes admin and trainer, `requireRole('admin' | 'trainer' | 'student')` that role only; `requireAdmin()` (`src/lib/auth/require-role.ts`) is an active admin or a redirect (a trainer goes to `/staff`). `requireRole` also redirects to `/login` for a missing or deactivated profile.
- `profiles.trainer_id` (the student's trainer, FK `on delete restrict`, so a trainer who still has students cannot be deleted) and `profiles.active` (false = deactivated staff). Neither is writable by a session (0025/0026): only the service role writes them.
- Database helpers in schema `private` (policies call them): `is_staff()` (active admin or trainer), `is_admin()`, `manages_student(uuid)` (admin for any existing student, a trainer for students whose `trainer_id` is theirs; uses `auth.uid()`), `manages_attempt(uuid)`, and (0027) `staff_manages_student(p_staff, p_student)`, the same rule for an explicit staff id (the service-role functions get the staff id as an argument). The target must have role `student`, so a nonexistent id or a staff id is "not managed". `service_role` has USAGE on schema `private` (0027) so the functions can call it. `give_extra_attempts`, `remove_curriculum` and `reorder_curriculums` raise `not_staff`, then `not_your_student` (also for a nonexistent student id); TypeScript maps it (`src/lib/extra-attempts.ts`, `src/app/staff/grants/messages.ts`, the student actions).
- Scope: RLS on `profiles`, `assignments`, `attempts`, `attempt_questions`, `answers` and `student_details` uses `manages_student`, so a trainer sees only their own students. Curriculums, exam sets and questions: every staff user reads, only an admin writes (insert/update policies use `is_admin()`). Admin-only in the app: `/staff/curriculums` (+ `[id]`), `/staff/questions`, `/staff/team`, every curriculum, exam set and question action, `assignTrainer`, `deleteStudent` and the Team actions (all call `requireAdmin()` first). Trainers get Dashboard, Attempts, Blocked, Extra attempts and Students (`visibleNav` in `src/app/staff/staff-nav.tsx`, `adminOnly` entries are hidden from them; the student page hides links they cannot use). Trainers can give extra attempts, reset passwords, add/remove/reorder curriculums, edit details, resend invites and import students for their own students only.
- Trigger `handle_new_user` (deferred constraint trigger, 0003) also reads `raw_app_meta_data.trainer_id` (admin API only; a missing, malformed or non-staff id stays null) and maps a legacy role value `staff` to `admin`, so older scripts keep working. Student accounts are created with `createStudentAccount(client, student, { trainerId })` (`src/lib/staff-students.ts`): the owner goes into app metadata at creation, because a trainer's RLS insert of the first assignment needs the owner in place. A trainer's students always belong to that trainer; an admin picks an active trainer or none (`resolveOwner` in `students/actions.ts`; `findActiveTrainer`).
- `student_details` (0026, 0027): personal data per student (contact email required; phone, guardian, date of birth, gender, address, passport number and expiry, destination country, target intake, German level A0..C1, qualification, joined on, programme start, status active/on_hold/completed/dropped, notes). It is a separate table so ordinary student/staff reads of `profiles` never carry passport or contact data: RLS select/insert/update only through `manages_student`, students and anon read nothing, no DELETE (the row goes with the student: `student_id` references `profiles` on delete cascade, which is also how `deleteStudent` erases it). UPDATE is column-level (not `student_id`, `created_at`, `updated_at`, 0027), so `saveStudentDetails` (`details-actions.ts`) runs under the staff session and is update-then-insert (no upsert). `batch` and `track` stay on `profiles`. Validation is `validateStudentDetails` (`src/lib/student-details.ts`, shared by form and CSV; phone check is loose, dates use the India calendar day). `updated_at` has no trigger. Never log details.

## Invites and mail (v2 phase 1)
- A student (or trainer) gets an emailed link to choose their own password. `INVITE_LIFETIME_HOURS = 24` (`src/lib/invite-link.ts`) is what the mail says; it must equal Auth's email OTP expiry: `[auth.email] otp_expiry = 86400` in `supabase/config.toml` (restart the local stack after changing it) and the same 86400 s in the hosted dashboard (hosted Auth allows at most 86400 and defaults to 1 hour).
- `buildInviteLink(admin, userId, appUrl)` reads the Auth user's email (`getUserById`; trainers have a real email, students an internal one), calls `generateLink({ type: 'recovery' })` and returns `${APP_URL}/set-password?token_hash=...`. Making a link does not use it up: the token is consumed only when the new password is POSTed (`setPasswordAction`, `src/app/set-password/actions.ts`, `verifyOtp` then `updateUser`, other sessions ended, redirect to `/login`), never on opening the page, because mail scanners prefetch links. `/set-password` is public (`public-paths.ts`). Every token problem gives one message ("This link is no longer valid..."). A weak password does not burn the token (checked first by `checkPassword`).
- `src/lib/invites.ts`: `sendInvite(studentId)` returns `sent | failed | skipped` (skipped = no contact email; reads `student_details.contact_email`), `sendAccountInvite(userId)` is the trainer variant (Auth email, shows the email as the sign-in name), `createInviteLink`. They never throw and never log or return the link. `resendInvite(studentId)` (`students/actions.ts`, staff, own students) and `resendTrainerInvite` (admin) make a fresh link each time. A failed mail never undoes the account; staff resend. The student page Invite card (`invite-status`) only says where invites go or that there is no contact email; whether the student has chosen a password is not tracked.
- Mail module `src/lib/mail` (`sendMail`, `buildInviteMail`): transports `log` (default outside production: nothing sent, logs only the recipient domain) and `resend` (REST call with an 8 s timeout; needs `RESEND_API_KEY` and `MAIL_FROM`). In production `MAIL_TRANSPORT` must be set on purpose (empty fails with a logged reason). The body and the link are never logged. English copy only.
- CSV: caps are bytes (questions 2 MB, students 1 MB) and `STUDENT_CSV_MAX_ROWS = 200` students per file (`src/lib/csv/limits.ts`; each created student is followed by an invite mail, so an import must fit the function time limit). Optional columns `contact_email`, `phone`, `passport_number`, `destination_country`, `german_level`, `programme_start`; with a contact email the details are saved too. `importStudents(csv, { trainerId })` sends the invites after the import and reports counts (invited, no email, failed with usernames); an admin chooses the trainer for the whole file.

## Team (trainers, admin only)
- `/staff/team` lists trainers (name, email, active, student count) with Add a trainer, Resend invite, Deactivate / Reactivate and Move students. `src/app/staff/team/actions.ts`, each action calls `requireAdmin()` first: `createTrainer({ email, username, fullName })` (Auth user with `role: 'trainer'` and a random password nobody sees, then `sendAccountInvite`; trainers sign in with their email), `resendTrainerInvite` (refuses an inactive trainer), `setTrainerActive(id, active)`, `reassignStudents({ fromTrainerId, toTrainerId })` (to an active trainer, one update). `assignTrainer({ studentId, trainerId })` (`students/details-actions.ts`, admin) sets or clears one student's trainer (active trainer only).
- Deactivate order: refuse while the trainer has students (reassign first); set `profiles.active = false` first (every policy and `requireRole` treat the account as gone at once); re-check for a student assigned in between (undo and refuse if one appeared); then the Auth ban (`ban_duration` about 100 years); then `revoke_user_sessions`. A failure part-way leaves the account inactive, never banned-but-active; retrying finishes it. Reactivate lifts the ban first and sets `active` last. There is no database guard against assigning a student to an inactive trainer (app-level check only).
- Login (`src/app/login/actions.ts`) and the proxy treat an inactive profile like a wrong password / a missing profile (generic error, session ended).
- `scripts/create-staff.ts` takes `STAFF_ROLE=admin|trainer` (default `admin`) next to the existing variables (see the production checklist).

## Staff management (Task 8)
- Pages: `/staff/students` (search, batch/track filter, Add student, Import CSV with preview), `/staff/students/[id]` (curriculums with order, effective status, attempts "x of y used" with "2 per student" or "2 + 1 extra", exam sets left or "Repeats allowed"; Give extra attempts; add/remove/reorder; reset password; delete), `/staff/curriculums` ("N attempts per student", "Too few exam sets" and "Too few questions" badges), `/staff/curriculums/[id]` (Curriculum settings: name and "Attempts per student" 1..20; exam set settings; `curriculum-warning` when fewer usable exam sets than attempts), `/staff/questions` (filters, pool sizes vs questions per paper, manual bilingual form, approve/draft, CSV import). Readers in `src/lib/staff-manage.ts` (staff session, RLS).
- Actions (each calls `requireRole('staff')` unless the roles section says admin only, takes plain objects, returns `{ ok, ... }`): `students/actions.ts` (`createStudent`, `previewStudentsImport`, `importStudents`, `resetPassword`, `assignCurriculum`, `removeCurriculum`, `reorderCurriculums`, `deleteStudent`), `curriculums/actions.ts` (`saveCurriculum({ id?, name, maxAttempts? })` validated by `validateCurriculumFields`, a rename keeps max_attempts; `saveExamSet`), `questions/actions.ts` (`saveQuestion`, `setQuestionStatus`, `previewQuestionsImport`, `importQuestions`), `grants/actions.ts` (`giveExtraAttemptsAction`). Writes use the staff session except auth users and passwords (Auth admin API, `src/lib/staff-students.ts`) and every assignment change after its creation: staff sessions cannot update or delete assignments (0023), so extra attempts, reorder and removal go through the service-role functions `give_extra_attempts`, `reorder_curriculums` and `remove_curriculum`, and attempts through `start_attempt` / `record_score` (service role).
- New students: auth user with app_metadata `{ role: 'student', username, full_name, batch?, track }`; track `nursing` gets "Pflege Ausbildung" (1) and "Life in Germany" (2), `other` gets "Life in Germany" (seeded by migration 0010, looked up by their fixed ids, so renaming is safe). If assignments fail the user is deleted again. Passwords are never logged, put in URLs or returned; tests assert results never contain them.
- `resetPassword` changes the password with the admin API, then ends every session with `revoke_user_sessions` (0011, service role only; deletes `auth.sessions`, refresh tokens cascade). Passwords must not start or end with whitespace (`checkPassword`, shared by form and CSV; the CSV reader passes the password untrimmed via `rawCell`). CSV caps are bytes (`src/lib/csv/limits.ts`: questions 2 MB, students 1 MB); `experimental.serverActions.bodySizeLimit` is 5mb.
- `deleteStudent(studentId, { confirmUsername })` is the DPDP erasure path: staff type the username, it refuses while an exam is in progress (expired ones are closed first), then deletes the auth user with the Auth admin API; the cascades remove profile, assignments (with their extra attempts), attempts, answers and the scoring snapshot. Staff accounts are not deleted here.
- `reorderCurriculums` and `removeCurriculum` write through the service-role SQL functions `reorder_curriculums` and `remove_curriculum` (0016, remove replaced in 0021 without grants; staff id from the session, `not_staff` otherwise), so each change is one transaction: reorder sets all positions at once (`order_mismatch` unless the list is exactly the student's curriculums; the order is only the display order, not a sequence); remove locks the assignment row and deletes it.
- Removing a curriculum and adding it again resets the student's assignment: status open, `extra_attempts` 0, repeats off; earlier attempts still count as used. So a passed curriculum can be taken again while attempts are left (a staff-only action behind a confirm when attempts exist).
- `removeCurriculum` refuses while an attempt in the curriculum is in progress; with attempts it needs `{ confirm: true }` and then deletes only the assignment (with its extra attempts; attempts stay and still count if it is added again).
- Validation is shared: `validateQuestionFields` (`src/lib/question-fields.ts`) for CSV and manual questions, `validateStudentFields`/`parseStudentsCsv` (`src/lib/csv/students.ts`), `readCsvRows` (`src/lib/csv/rows.ts`) for both CSV parsers, `validateExamSetFields`/`examSetWarnings`/`poolWarning`/`curriculumWarnings`/`validateCurriculumFields` (`src/lib/exam-set-fields.ts`; topic mix counts must add up to question_count; pool warning when approved < questions per paper). Question import is all-or-nothing by default (one insert); "only valid rows" is an explicit choice; stems already in the exam set are row errors.
- Next 16 keeps visited routes in the DOM hidden (Activity): in e2e prefer role locators over `getByLabel`, and `filter({ visible: true })` for student cards (`curriculumCard()` in `e2e/helpers.ts`).

## Auth and sessions
- Next 16 uses `src/proxy.ts` (the renamed middleware) for auth redirects: unauthenticated to `/login`, students to `/consent` until `consent_at`, staff and students kept to their own areas. It calls `getUser()` so a session ended by a newer login is rejected at once.
- Exam server actions (`startExam`, `saveAnswerAction`, `submitExam`) call `requireStudentWithConsent()` (`src/lib/auth/require-role.ts`): a student without `consent_at` is redirected to /consent and nothing runs (the proxy only covers page requests). Only the consent action itself uses plain `requireRole('student')`.
- Login ends other sessions (`signOut({ scope: 'others' })`). An Auth rate-limit error (status 429) gets its own message ("Too many sign-ins, please wait a minute and try again."), never "incorrect password". Consent is written by a server action with the service role.
- Pages that read the session call `requireRole()` (which awaits `connection()`) inside `<Suspense>`, as required by `cacheComponents`.
- e2e (`npm run test:e2e`) needs the local stack and `.env.local`; it seeds test users with the service role (`e2e/seed.ts`).
